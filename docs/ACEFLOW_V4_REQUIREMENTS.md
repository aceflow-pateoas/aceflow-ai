## 产品定位

### 核心定位
AceFlow 是一个**轻量级工作流管理系统** + **项目记忆系统**

### 产品边界

**✅ AceFlow 要做的**：
- 结构化工作流管理
- 项目特定知识管理（技术决策、经验教训）
- 状态和任务追踪
- 跨对话上下文保持

**❌ AceFlow 不做的**：
- 不接入大模型（依赖外部 AI）
- 不做代码智能分析
- 不做通用知识库（依赖大模型能力）
- 不做复杂的代码工具

### 技术架构
```
用户 ←对话→ AI（Claude/GPT/etc）
              ↓ MCP 工具调用
         AceFlow MCP Server
              ↓
    WorkflowEngine + MemoryManager + StateManager
```

**关键约束**：
- AceFlow 是被动响应方，不能主动引导对话
- 通过工具返回值和提示词影响 AI 行为
- 依赖大模型的理解和决策能力

## 核心痛点与优先级

基于对个人开发者和小型团队的分析，四大痛点优先级：

| 痛点 | 优先级 | 说明 |
|------|--------|------|
| **C. 缺少结构化开发流程** | **P0** | 最优先解决，项目容易混乱 |
| **A. AI 经常失忆** | **P1** | 次优先，影响开发效率 |
| **B. 代码质量不稳定** | **P2** | 重要但可后续改进 |
| **D. 知识无法共享** | **P3** | 团队协作需要，可延后 |

### 痛点 C 的细化问题（按重要性排序）

1. **B - 阶段设计不合理**：实际开发用不上现有的 7/10 个阶段
2. **C - 流程太死板**：无法根据具体项目调整
3. **E - AI 指导不够具体**：提示词不实用
4. **A - 模式太多**：不知道选哪个
5. **D - 缺少可视化**：不知道进度

## 工作流设计

### 实际工作流程（用户真实场景）

用户通常是：
```
1. 输入需求描述（PRD/功能说明）
2. AI 输出设计方案（接口、逻辑、技术方案）
3. 写代码
4. 测试验证
5. 更新任务状态
```

**关键洞察**：
- ✅ 用户会一次性给出需求描述，不需要 AI 反复澄清
- ✅ 设计方案重点：核心逻辑 > 接口定义 > 数据结构 > 技术选型 > 风险提示
- ✅ 测试验证要求：透明汇报、问题分类、主动建议

### MVP 支持的 6 种工作流

#### 1. 功能开发（Feature Development）

**触发**：用户要实现新功能

**阶段流程**：
```
需求梳理 → 设计方案 → 编码实现 → 功能测试 → 完成交付
```

**各阶段检查清单**：

**需求梳理**：
```
□ 接口定义已输出（API路径、入参、出参、错误码）
□ 核心逻辑已设计（伪代码或流程描述）
□ 技术方案已确认（使用的库、存储方案、架构模式）
□ 潜在问题已识别（性能、安全、并发等）
```

**设计方案**：
- 输出核心逻辑（伪代码/流程图）
- 输出接口定义
- 输出数据结构设计
- 输出技术选型说明
- 输出潜在风险

**编码实现**：
- 先展示代码骨架（函数签名、类结构）
- 用户确认后填充实现
- 一个文件一个文件生成

**功能测试**：
- 详细汇报测试结果
- 失败时：分析原因 + 提供2-3个修复方案
- 发现潜在问题时主动询问

**特点**：
- ✅ 支持子任务追踪
- ✅ AI 初始拆解任务 + 用户确认
- ✅ 支持动态添加任务

---

#### 2. Bug修复（Bug Fix）

**触发**：修复已知问题

**阶段流程**：
```
问题定位 → 修复方案 → 编码修复 → 回归测试 → 完成交付
```

**问题定位检查清单**：
```
□ 问题根因已分析
□ 影响范围已评估
□ 复现步骤已确认
□ 相关代码已定位
```

**特点**：
- ❌ 不支持子任务追踪（整体推进）
- ✅ 单个 bug 是独立工作项
- ✅ 多个 bug 并行追踪

---

#### 3. 重构优化（Refactoring）

**触发**：性能优化、代码重构

**阶段流程**：
```
现状分析 → 优化设计 → 编码重构 → 性能验证 → 完成交付
```

**现状分析检查清单**：
```
□ 当前问题已识别
□ 性能基准已确定
□ 优化目标已明确
□ 改造风险已评估
```

**特点**：
- ❌ 不支持子任务追踪
- ✅ 单个优化项是独立工作项

---

#### 4. 代码审查（Code Review）

**触发**：审查 PR/代码变更

**阶段流程**：
```
理解变更 → 检查清单审查 → 输出审查意见
```

**检查清单**：
```
□ 功能正确性：是否实现需求
□ 代码规范：命名、格式、注释
□ 测试覆盖：是否有测试、覆盖是否充分
□ 性能影响：是否有性能问题
□ 安全风险：是否有安全漏洞
□ 可维护性：代码是否清晰、易理解
```

**输出**：
- 审查意见（通过/需修改/拒绝）
- 具体问题列表 + 修改建议

**特点**：
- ❌ 不支持子任务追踪
- ✅ 检查清单本身就是任务

---

#### 5. 文档编写（Documentation）

**触发**：补充缺失的文档（非接口文档）

**用途**：
- 给老代码补文档
- 填补工作流中遗漏的部分
- 使用手册、部署文档等

**阶段流程**：
```
确定大纲 → 逐章编写 → 补充示例 → 审查发布
```

**大纲检查清单**：
```
□ 文档目标已明确（给谁看、解决什么问题）
□ 章节结构已确定
□ 重点内容已列出
```

**特点**：
- ❌ 不支持子任务追踪
- ✅ 多个文档作为独立工作项

**注意**：接口文档应该在"功能开发 → 设计方案"阶段产出

---

#### 6. 性能排查（Performance Debug）

**触发**：系统响应慢，需要定位瓶颈

**阶段流程**：
```
问题描述 → 快速定位 → 验证假设 → 给出方案
```

**问题描述检查清单**：
```
□ 性能问题已明确（什么操作慢、慢多少）
□ 复现条件已确认
□ 性能基线已记录
```

**快速定位**：
- AI 分析代码找可疑点
- 列出可能的瓶颈（循环、查询、IO、网络）
- 按优先级排序

**特点**：
- ❌ 不支持子任务追踪
- ✅ 线性排查，找到瓶颈即停止

---

### 工作流选择机制

**用户输入示例**：
```
"实现用户登录功能"
"修复注册验证码问题"
"优化首页加载速度"
```

**AI 识别流程**：
```
1. AI 分析用户输入
2. AI 识别工作类型："这看起来是功能开发/Bug修复/..."
3. 询问用户确认："是功能开发吗？"
4. 用户确认后，调用 start_iteration(type="feature", goal="...")
5. AceFlow 返回对应工作流的模板
```

## 任务追踪机制

### 两层追踪结构

#### 第一层：工作项列表（所有工作流）

**定义**：当前项目所有进行中/待开始/已完成的工作

**示例**：
```
项目工作列表：
├─ #1 [功能] 用户登录功能 - 进行中（编码实现阶段）
├─ #2 [Bug] 修复注册验证码 - 待开始
├─ #3 [Bug] 修复密码重置超时 - 待开始
├─ #4 [优化] 登录性能优化 - 已完成
├─ #5 [审查] Review PR#123 - 进行中
└─ #6 [文档] 编写部署文档 - 待开始
```

**特点**：
- 每个工作项独立追踪
- 支持多个工作项并行
- 记录工作类型、状态、当前阶段

---

#### 第二层：子任务列表（仅功能开发）

**定义**：单个功能开发工作项内部的任务拆解

**示例**：
```
#1 [功能] 用户登录功能
  当前阶段：编码实现
  子任务：
  ├─ Task 1: 实现登录API endpoint ✅ 已完成
  ├─ Task 2: 实现Token生成逻辑 ⏳ 进行中
  ├─ Task 3: 实现密码验证逻辑 ⏸️ 待开始
  └─ Task 4: 实现错误处理 ⏸️ 待开始
```

**支持场景**：
- ✅ 功能开发：需要拆分子任务
- ❌ Bug修复：不拆子任务，整体推进
- ❌ 重构优化：不拆子任务
- ❌ 代码审查：不拆子任务（检查清单即任务）
- ❌ 文档编写：不拆子任务（多文档分工作项）
- ❌ 性能排查：不拆子任务（线性排查）

### 任务管理流程

#### 初始任务拆解（功能开发）

**流程**：
```
用户："实现用户登录功能：
- 支持账号密码登录
- 返回JWT Token
- 密码错误3次锁定"

  ↓

AI 分析需求后提出任务拆解：
"我建议拆分为以下任务：
1. 实现登录API endpoint
2. 实现Token生成逻辑
3. 实现密码验证逻辑
4. 实现防暴力破解机制
5. 实现错误处理

是否确认？"

  ↓

用户确认 → AI 调用工具创建任务列表
```

---

#### 动态添加任务

**触发**：执行过程中发现需要新任务

**流程（版本3：混合确认）**：
```
用户："需要加个验证码校验"

  ↓

AI："我建议添加新任务：实现验证码校验
插入位置：Task 2（Token生成）之后"

  ↓

系统弹出确认：
┌─────────────────────────────┐
│ 📝 添加新任务                │
├─────────────────────────────┤
│ 任务名称: 实现验证码校验      │
│ 插入位置: Task 2 之后         │
│                              │
│ [确认] [取消]                │
└─────────────────────────────┘

  ↓

用户确认后，AI 开始对话式补充任务要求：
"关于验证码校验，请补充以下信息：
1. 使用图形验证码还是短信验证码？
2. 过期时间？
3. 防暴力破解策略？"

  ↓

AI 根据用户回答完善任务详情
```

**任务要求补充（对话式）**：
- AI 根据任务类型智能提问
- 优先推断（基于项目记忆和通用知识）
- 只问关键问题，减少用户负担

**示例**：
```
AI："验证码用图形还是短信？
其他参数我按项目惯例设置：
- 5分钟过期（行业标准）
- Redis存储（项目已有）
- 3次失败锁定10分钟（参考登录逻辑）

你可以调整任何参数。"
```

**判断标准组合（A+B+C）**：
- A. 任务类型识别（如"验证码"→ 安全功能）
- B. 项目上下文（项目已有Redis、之前的防暴力破解策略）
- C. 通用知识（验证码通常5分钟过期 - 依赖大模型）

---

#### 任务完成确认

**流程（版本3：混合模式）**：
```
AI 完成 Task 1: 实现登录API

  ↓

AI 调用工具：suggest_task_completion(task_id="task_1")

  ↓

系统在对话中提示：
"💡 AI 建议标记 Task 1 为完成，是否确认？
[确认完成] [需要修改] [忽略]"

  ↓

用户选择：
- 确认完成 → 标记 Task 1 ✅
- 需要修改 → 继续工作
- 忽略 → 继续对话
```

**关键设计**：
- ✅ AI 主动建议（不会忘记）
- ✅ 用户最终确认（质量保证）
- ✅ 工具调用保证状态更新（结构化）

### 强制状态更新机制

**问题**：AI 可能忘记更新阶段/任务状态

**原因分析**：
- A. Prompt 太长，AI 注意力不够
- D. 没有强制检查机制

**解决方案（优先级1）**：
```
在工作流每个阶段结束时，强制触发更新工具

实现方式：
- 工具返回值中提示下一步操作
- 工具 description 中强调必须调用
- AI 主动调用 suggest_stage_completion() 触发用户确认
```

**备选方案（2和3）**：
- 方案2：AI 输出前自动检查状态是否更新
- 方案3：状态变成结构化 JSON，AI 只能通过工具修改

## 质量检查机制

### 核心原则

**不造假原则**：
> "不要陷入问题然后为了通过而造假掩盖问题真相"

**反面案例**：
- ❌ 跳过失败的测试
- ❌ 用 try-catch 包裹所有错误
- ❌ 修改测试用例而不是修复代码
- ❌ 用注释 `# TODO: fix this` 糊弄过去

**正面原则**：
- ✅ 透明汇报所有问题
- ✅ 智能分类（能自动修 vs 需人决策）
- ✅ 主动建议改进

### 测试验证阶段的汇报机制

#### 场景 A：全部通过

**选项2（详细报告）**：
```
✅ 所有测试通过（3/3）

详细结果：
1. ✅ test_login_success - 认证成功场景
2. ✅ test_login_wrong_password - 密码错误处理
3. ✅ test_login_user_not_found - 用户不存在处理

执行时间：1.2s
```

---

#### 场景 B：部分失败

**选项2+3组合**：

**先分类问题**（选项3）：
```
测试结果：2通过 / 1失败

✅ 通过：
- test_login_success
- test_login_user_not_found

❌ 失败：
- test_login_wrong_password
  错误：密码验证逻辑有误

问题分类：
🔧 可自动修复：
  - 无

⚠️ 需要决策：
  - 密码验证逻辑：当前使用明文比对，应该用bcrypt
```

**然后给出方案**（选项2）：
```
修复方案建议：

方案1：使用 bcrypt 加密比对（推荐）
- 优点：安全、标准做法
- 缺点：需要引入 bcrypt 库
- 影响：需要修改密码存储逻辑

方案2：使用简单哈希（SHA256）
- 优点：无需额外库
- 缺点：不够安全（无盐值）

方案3：暂时保持明文（不推荐）
- 仅用于开发测试

请选择方案，或提出其他想法。
```

---

#### 场景 C：发现潜在问题

**选项2（主动询问）**：
```
✅ 所有测试通过

⚠️ 潜在问题发现：
- 并发登录场景未测试
- 密码重试计数未考虑分布式场景（多服务器）
- Token刷新逻辑缺失

是否需要我补充以下测试/功能？
□ 并发登录测试
□ 分布式计数器（Redis）
□ Token刷新机制

请选择需要补充的项目。
```

### 代码生成策略

**期望交互顺序（D > C > B）**：

**D - 先骨架后实现**：
```
AI："我先展示代码结构：

// login.controller.ts
class LoginController {
  async login(req, res) { }
  async validatePassword(password, hash) { }
  async generateToken(user) { }
}

结构确认后，我会填充每个函数的实现。"
```

**C - 核心优先**：
```
先生成核心函数/类，测试通过后再补充其他部分
```

**B - 逐文件生成**：
```
一个文件一个文件地生成，每个都确认后再继续
```

### 自动检测机制

**AI 自己能检测的问题（静态检查）**：
```
生成代码后，AI 自动运行：
1. 语法检查（TypeScript/ESLint）
2. 类型检查（mypy/TypeScript）
3. 代码规范（Prettier/Black）
4. 基础测试（单元测试）

发现问题 → 自动修复 → 汇报修复内容
```

**需要用户决策的问题**：
```
遇到以下情况，必须询问用户：
1. 技术选型（用哪个库）
2. 架构决策（用什么模式）
3. 安全策略（如何加密）
4. 性能权衡（时间vs空间）
5. 测试失败且无明确修复方案
```

**透明汇报**：
```
AI 必须清楚说明：
- 发现了什么问题
- 自动做了什么修复
- 哪些问题无法自动解决
- 给出2-3个人类决策方案
```

## 记忆系统

> **备注**：本部分需要后续深入设计，参考 Cline Memory Bank 机制

### 基本原则

**记忆来源（B+C）**：
- ✅ B. 项目历史决策（AceFlow 记录）
- ✅ C. 代码库信息（AI 自己读取，AceFlow 不做复杂分析）
- ❌ A. 通用知识库（依赖大模型能力）

**记忆类型**：
- 技术决策
- 经验教训
- 输出文档路径

---

### 记忆内容

**记录什么**：
```json
{
  "功能": "用户登录",
  "完成时间": "2025-01-15",

  "技术决策": {
    "认证方案": "JWT",
    "Token过期": "30分钟",
    "存储": "Redis",
    "决策原因": "无状态，适合微服务"
  },

  "经验教训": {
    "问题": "bcrypt性能瓶颈",
    "解决": "10轮→8轮",
    "注意": "需要防暴力破解"
  },

  "输出文档": [
    "docs/api/login.md",
    "docs/design/auth-design.md"
  ]
}
```

**不记录什么**：
- ❌ 接口详细定义（记录文档路径即可）
- ❌ 代码细节（读代码即可）
- ❌ 所有对话内容（太冗余）

---

### 记忆提炼机制

**触发时机（D + 用户主动）**：

**D - AI 检测到关键决策**：
```
用户："我们用JWT认证，30分钟过期"

  ↓

AI 识别关键决策：
"💾 检测到技术决策，是否记录到记忆库？
[记录] [忽略]"

  ↓

用户确认 → AI 提炼信息 → 展示给用户 → 用户修改/确认 → 写入
```

**用户主动**：
```
用户："保存这个决策"
用户："记录这个经验"

  ↓

AI 提炼关键信息 → 展示 → 用户确认 → 写入
```

---

### 关键决策判断标准（A+B+C）

**判断"是否值得记录"**：

✅ **满足以下任意2个以上条件**：
- A. 包含决策关键词（选择、决定、使用、采用、方案）
- B. 影响范围广（多模块、长期维护、架构级）
- C. 技术选型类（库、框架、架构模式、存储方案）

**示例**：
```
✅ "用JWT认证，30分钟过期" - 满足A+C
✅ "所有错误用统一ErrorHandler处理" - 满足A+B
❌ "把这个变量改成userName" - 都不满足
❌ "这个函数换个名字" - 都不满足
```

## 技术架构约束

### 角色边界

```
用户 ←→ AI（主动方）
         ↓ 调用工具
    AceFlow MCP Server（被动方）
         ↓
    提供：工具 + 资源 + 提示词
```

**AceFlow 的能力**：
- ✅ 提供工具（start_iteration, complete_task, ...）
- ✅ 返回结构化数据
- ✅ 返回提示词模板
- ✅ 管理状态和记忆
- ❌ 不能主动引导对话
- ❌ 不能强制 AI 调用工具
- ❌ 不接入大模型做智能分析

**依赖大模型的能力**：
- 理解用户需求
- 识别工作类型
- 拆解任务
- 生成代码
- 判断何时调用工具
- 提炼关键信息

---

### 提示词设计原则

**检查清单式提示词**（最有效）：
```
需求梳理阶段检查清单：
□ 接口定义已输出（API路径、入参、出参）
□ 核心逻辑已设计（伪代码或流程）
□ 技术方案已确认（库、存储、架构）
□ 潜在问题已识别（并发、安全等）

全部完成后调用 complete_stage()。
```

**分场景模板**：
- 每种工作流有专门的阶段模板
- 每个阶段有明确的检查清单
- 包含必要的工具调用提示

---

### 状态持久化

**存储结构**：
```
.aceflow/
├─ state/
│  └─ {project_id}/
│     ├─ work_item_001.json  (工作项状态)
│     ├─ work_item_002.json
│     └─ ...
├─ memory/
│  └─ {project_id}/
│     ├─ decisions.json      (技术决策)
│     ├─ lessons.json        (经验教训)
│     └─ ...
└─ config.yaml               (项目配置)
```

**访问方式**：
- 通过 StateManager API 读写状态
- 通过 MemoryManager API 读写记忆
- 不允许直接修改文件
