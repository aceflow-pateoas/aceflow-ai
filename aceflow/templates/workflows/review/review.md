# 代码审查阶段 (Code Review)

## 检查清单 (Checklist)

### 必须完成 (Required)

- [ ] **代码逻辑已审查**
  检查代码逻辑是否正确、清晰

- [ ] **代码规范已检查**
  命名、格式、注释是否符合规范

- [ ] **潜在问题已识别**
  发现并记录潜在的Bug、性能问题、安全隐患

- [ ] **审查意见已提交**
  在PR中添加审查评论

- [ ] **审查结论已给出**
  批准(Approve) / 需要修改(Request Changes) / 仅评论(Comment)

### 可选项 (Optional)

- [ ] **代码运行验证**
  拉取代码到本地运行验证

- [ ] **性能影响评估**
  评估代码变更对性能的影响

## 输出物 (Deliverables)

1. **审查评论**（PR中的comments）
2. **问题清单**（需要修改的问题列表）
3. **审查结论**（Approve/Request Changes/Comment）
4. **建议改进**（可选的优化建议）

## 审查维度 (Review Dimensions)

### 1. 代码正确性
- ✅ 实现了需求的功能
- ✅ 边界条件处理正确
- ✅ 错误处理合理
- ✅ 没有明显的Bug

### 2. 代码质量
- ✅ 命名清晰有意义
- ✅ 函数职责单一
- ✅ 代码结构清晰
- ✅ 没有过度复杂的逻辑
- ✅ 没有重复代码

### 3. 测试覆盖
- ✅ 新增代码有测试
- ✅ 测试用例充分
- ✅ 边界场景已测试
- ✅ 测试代码质量良好

### 4. 性能考量
- ✅ 没有明显的性能问题
- ✅ 算法复杂度合理
- ✅ 没有不必要的计算
- ✅ 资源使用合理

### 5. 安全性
- ✅ 输入验证完善
- ✅ 没有SQL注入风险
- ✅ 没有XSS漏洞
- ✅ 敏感信息处理得当
- ✅ 权限控制正确

### 6. 可维护性
- ✅ 代码易于理解
- ✅ 注释适当清晰
- ✅ 模块职责明确
- ✅ 依赖关系合理

## 审查评论指南 (Comment Guidelines)

### 评论类型

**阻塞性问题** (Blocking)
```
🔴 [Blocking] 这里存在潜在的空指针异常，需要添加null检查。
```

**建议性改进** (Suggestion)
```
💡 [Suggestion] 建议将这个长函数拆分为多个小函数，提升可读性。
```

**疑问** (Question)
```
❓ [Question] 为什么这里使用了递归？是否有性能考虑？
```

**赞赏** (Praise)
```
👍 [Praise] 这个错误处理很完善！
```

### 评论原则

1. **具体明确**: 指出具体的代码行和问题
2. **建设性**: 提供改进建议，而不只是批评
3. **友好尊重**: 使用友好的语气
4. **可操作**: 给出明确的修改方向

## 审查结论标准 (Review Decision Criteria)

### ✅ Approve (批准)
- 没有阻塞性问题
- 代码质量达标
- 测试覆盖充分
- 可以合并到主分支

### 🔄 Request Changes (需要修改)
- 存在阻塞性问题
- 必须修复后才能合并
- 需要提交者处理

### 💬 Comment (仅评论)
- 提供建议但不阻塞合并
- 留待后续优化
- 或者需要更多讨论

## 完成标准 (Completion Criteria)

- 代码已全面审查
- 审查意见已提交
- 审查结论已给出
